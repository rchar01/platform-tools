# Agent Notes

## Agent Workflow Expectations

- Read relevant code before editing.
- Prefer minimal changes that match existing patterns.
- Keep `README.md`, `AGENTS.md`, and skill docs current when repository behavior changes.
- If your runtime provides specialized tools or subagents for codebase exploration, use them when the repository structure, ownership boundaries, or relevant files are unclear.
- If your runtime provides specialized tools or subagents for verification, use them for non-trivial test runs, runtime-backed checks, or command-heavy validation.
- If your runtime provides specialized tools or subagents for review, use them after substantial edits to catch regressions, missing updates, or doc/code drift.
- If your runtime provides specialized tools or subagents for research, use them when behavior depends on external tooling or upstream docs.
- Prefer local repository docs, scripts, and configuration first; use web research when local sources are insufficient or freshness matters.
- Summarize any specialist-tool or subagent findings you rely on.
- Do not revert unrelated worktree changes.

## Repository Shape

- This repo is a collection of maintained Bash and Python helper tools in `bin/`; `Makefile` is the source of truth for supported tools and local targets. Every maintained shell tool is Bashly-backed: source lives under `bashly/<tool>/`, while its generated and committed executable lives under `bin/`.
- Bashly workspaces use the standard colors library and `usage_colors` for TTY-only generated help. Preserve automatic pipe/redirect suppression and nonempty `NO_COLOR` support; this does not apply to application logs.
- PKI commands are maintained in `src/platform_pki/` and install templates from `templates/pki/`; frozen Bash evidence lives only under `tests/pki/oracles/` and is not a runtime dependency.
- Production PKI is unified-only: generate, install, document, and invoke only `platform-pki <command>`. The 18 v2 `platform-pki-*` aliases are removed, copied or renamed archives still behave canonically as `platform-pki`, and installation must fail before mutation when any exact legacy alias path exists without deleting it. Preserve legacy names only where exact bytes or historical evidence require them, including persisted actions such as `action=run platform-pki-ca-rollover recover`, protocol namespaces, hidden names, markers, archive names, frozen oracles, migration provenance, and historical v2 release entries; never broadly replace `platform-pki-` strings.
- `platform-runtime-evidence` is a state-free Bashly collector, not a `platform-pki` route. Preserve explicit reviewed identity, role, owner, execution status, and absolute installation boundary inputs; fixed-order percent-encoded schema-1 output; no-follow inspection of all 18 exact aliases; descriptor-bound artifact hashing with final identity stability; sealed exact-byte snapshot execution only when `--invoke-version` is explicit; descriptor-relative, nonrecursive exact cleanup of its one mode-700 probe directory; and the rule that it never reads PKI state. A successful collection is evidence, not role certification; fully present generic requirements report `role-review-required`.
- PKI host-local inventory requires exact target, validation-boundary digest, and rollback-hold scalars; managed entries reject them. Authenticated candidate verification/finalization/abandonment records accepted historical evidence only and never performs or claims live deployment.
- `platform-pki csr-trust-install` installs only the reviewed public protocol trust from `platform-private`; preserve exact policy fields, no-options Ed25519 signer validation, source-race checks, explicit lifecycle-through-inventory locking, atomic whole-directory publication, and the rule that installation itself performs no signing. Actual changes involving schema 2 require every retained candidate to have a fully authenticated immutable terminal outcome under current inventory and preserved migration state; historical responses and deployments authenticate against their immutable retained signer roots rather than proposed replacement trust. Malformed, conflicting, pending, or recovery-required candidate/outcome state fails closed, while exact no-ops and authenticated terminal history remain allowed.
- Host-local CSR signing uses strict ordered request and approval records, dedicated OpenSSH signature namespaces, inventory-authoritative profiles, permanently consumed replay records, certificate-only pending candidates, and the exact 114-field `state/csr/recovery-journal`. The public Python issue, migrate, and renewal writer in `src/platform_pki/service_issue.py` uses descriptor-bound CA passphrases, rechecks the exact journal, active authority directories, authority sources, inventory, and trust immediately before fixed-order publication of the seven CA database entries, and hands committed response publication to `src/platform_pki/csr_recover.py`. Renewal additionally authenticates exact bounded recursive finalized predecessor history through `src/platform_pki/csr_history.py`; globally enumerated retained candidates block replay unless every candidate's strict immutable finalized or abandoned outcome, retained transaction, replay, request and approval signatures, exact current schema-2 response and deployment trust roots, export, predecessor chain, current active-history membership, and current-inventory bindings all authenticate and survive the final source recheck. Every terminal must resolve to a non-`none` request in the current authenticated chain; abandoned issue or migration outcomes cannot satisfy renewal admission. Any pending candidate or orphan, malformed, unsafe, or conflicting outcome fails closed regardless of service, request, or predecessor. Pre-publication source replacement retains recoverable evidence without mutating CA state, pre-commit recovery restores exact CA state without reusing the request, and post-commit recovery never rolls back or re-signs and resumes exact response publication.
- `platform-pki offline-csr approve|sign` is the removable-media facade for exact host-local request and approval directories. Preserve explicit service/operation/request coordinates, untrusted no-follow input snapshots into protected local staging, authenticated stderr-only review, exact TTY confirmation or `--yes`, no-clobber five-file approval publication, compact fixed-order JSON success output, role-and-phase-labeled protected Ed25519 key prompting without passphrases in argv/environment/output, retained unbound approval-stage fail-closed inspection, and the pre-journal callback followed by complete source/absence rechecks that delegate every signing mutation and recovery rule to the authoritative host-local writer. Approval never mutates CA, replay, candidate, or target state; signing never exports or acts on a target and recovers only through `csr-recover`. Distinct requester/approver keys permit same-time-frame operation without claiming independent-human approval; identical keys retain the protocol delay.
- `platform-pki offline-workspace init` creates and validates only the exact owner-only removable-media custody/staging skeleton and fixed non-secret metadata. Keep its root component-wise disjoint from the known default authoritative PKI tree. Leaf payload descendants are workflow-owned opaque content that reruns never enumerate, authenticate, or claim; the initializer never creates keys, protocol payloads, transactions, symlinks, or authoritative signer replay/candidate/recovery state, and unsafe initializer-owned objects fail closed without repair.
- Operator-side host-local transport uses only `platform-pki direct-exchange` and `platform-pki gitlab-package`. Preserve pinned restricted SSH, sealed identity inputs, exact frame and file allowlists, bounded I/O, exact GitLab project and package coordinates, all-status enumeration, manifest-last publication, no-clobber download, token redaction, and the rule that transport never claims PKI authority or transfers `tls.key`. Target facades, account policy, sudo brokers, spools, and lifecycle mutation remain in `platform-config`; do not copy operator clients back there.
- `platform-pki inventory-install` must preserve exact outgoing byte-different inventories under the content-addressed owner-only `inventory/history/<sha256>.yml` store before replacing the active inventory. Retained CSR authentication may use only the exact signed snapshot, with current-file fallback solely when its digest matches, and must still require the selected current service policy to equal the historical entry. Never overwrite or garbage-collect inventory history automatically.
- Managed service issue/renew use the Python-only schema-1 journal at `state/service/recovery-journal` and retained transactions under `state/service/transactions/`; issue/renew use unified Python routes, and managed recovery is through `platform-pki service-recover --transaction`. `src/platform_pki/service_issue.py` implements public managed and host-local issue/renew orchestration, `src/platform_pki/service_writer.py` implements parser-valid forward journal transitions and exact planned publication with transaction-wide authenticated preflight, and `src/platform_pki/service_recover.py` implements public operational recovery. Preserve operation-specific replace/no-clobber policy, exact pre/stage/private-backup/publication/rollback identity-object-digest chains, prefix-bound staging and backup progress, the fixed private stage/input hierarchy, identity-journaled empty directory stages with atomic no-clobber publication, carried authenticated publication identities through the final evidence rewrite, authenticated inventory and issuer inputs, exact displaced-source bindings for every archive file, exact archive-container restoration, self-sized journal object state, canonical retained transaction/rollback-completion/terminal bytes, durable full-prefix rollback completion before rollback evidence is cleared, terminal-bound exact transaction and applicable rollback-completion evidence across journal removal, reverse-only rollback before commit, and cleanup-only recovery after commit. Final journal removal and journal-absent retries must enforce the one model-owned cleanup absence set: stage and backup for every terminal outcome, plus the exact retained-transaction renewal marker only for successful renewal. Same-name replacement never authorizes mutation, and destructive, staging, backup, publication, final evidence-handoff, or final cleanup-absence windows without authenticated resulting identity fail closed with the journal retained; host-local issue/migrate/renew continue to use the CSR journal and public `csr-recover`.
- Managed issue setup durably reserves its transaction before creating the private tree and atomically retains the exact reservation under `state/service/bootstrap-history/` at journal handoff or bootstrap-only recovery. Preserve exact retry from every bootstrap mutation boundary, strict authoritative terminal rollover-history parsing, active-issuer identity rechecks, OpenSSL config-value/path rejection before transaction mutation, and exact live certificate profile verification.
- `platform-pki certificate-export` publishes only an explicit authenticated pending CSR response to `export/certificates/v1/artifacts/<service>/<request-id>/`. Preserve exact current-inventory target binding, six-file mode-600 trees, canonical unfinalized manifests, descriptor-snapshotted retained signing-transaction response trust, lifecycle-through-export locking, same-parent no-clobber publication, final pre-output artifact/source identity rechecks, exact digest-pinned resolution, and the absence of current/latest inference or deployment finalization.
- `platform-pki csr-outcome` publishes only fully authenticated immutable finalized or abandoned signer outcomes to `export/csr-outcomes/v1/artifacts/<service>/<request-id>/`. Preserve the exact six-file mode-600 package, canonical signed outcome manifest, retained response-principal key binding, `platform-pki-csr-outcome-v1` signature namespace, lifecycle-through-export locking, same-parent no-clobber publication, exact idempotency, source/package reauthentication, digest-pinned resolution, and the rule that resolution reports historical terminal evidence without claiming live target state.
- `platform-pki export-ansible` atomically publishes one complete managed-key export from an exclusive same-parent mode-700 stage. Preserve no-follow identity-checked source copies, one inventory snapshot, service order and custody selection, descriptor-pinned exact custom marker authorization through exchange, exact no-clobber publication, forward-only exact-destination exchange, whole-tree durability and final rechecks, mutation-boundary exact-name displaced-tree cleanup, and reported retained private evidence whenever staging readiness or post-publication cleanup is uncertain.
- `platform-pki backup` is a Python-backed protected archive publisher. Preserve external GNU `tar`, inherited-terminal `age -p`, literal ordered recipients, full lifecycle-through-export locking, exact in-tree exclusions, mode-600 archives and canonical 14-field schema-2 receipts, no-clobber durable publication, and retained-archive evidence whenever receipt publication is incomplete.
- `platform-pki csr-candidate` requires schema-2 deployment trust for decisions, canonical nonce binding, fully authenticated recursive historical outcomes and active pointers, immutable outcomes, and source-complete exact-state resume-only finalization recovery. Preserve managed migration trees and all candidate/response/replay/transaction/export state.
- `platform-pki ca-rollover` is Python-backed for migration, status, preparation, and recovery. Preserve exact schema-2 and schema-5 journal compatibility, generation reservations, backup and trust snapshots, descriptor-bound passphrases, immutable candidate/state manifests, source-complete fault recovery, and lifecycle-through-export locking; retained Bash assets under `tests/pki/oracles/` are frozen differential evidence only.
- `platform-pki custody-report` is a Python-backed operationally read-only managed-layout audit. Preserve exact report bytes and ordering, compatible unordered 14-field receipts, identity-only archive binding without digest verification, descriptor-relative xdev metadata scans without path-list temporary files, at-most-257-byte identity-checked first-line PEM/age inspection, secret-free output, bounded suppressed storage helpers, explicit unknown operational controls, and lifecycle-through-export locking.
- `platform-pki ca-passphrase-verify` is a point-in-time active-generation check: keep passphrases off argv, environment, and output; pass them through a minimal inherited-descriptor boundary; suppress raw OpenSSL diagnostics; match each opened key to its active certificate; and never persist validation receipts.
- `platform-pki root-create` is a Python-backed schema-3 authority transaction writer. Preserve fixed writer-order journals and reservation/bootstrap bytes, ASCII recovery-record paths, lifecycle-through-root locking, descriptor-bound passphrase input, private complete staging, no-clobber authority publication, signal-safe mutation-to-evidence assignments, permanently consumed generation IDs, and final-Bash/Python interruption recovery through unified Python recovery.
- `platform-pki intermediate-create` is a Python-backed schema-3 authority and root-database transaction writer. Preserve fixed writer-order journals, root-scoped reservations, lifecycle-through-root-and-intermediate locking, separate descriptor-bound passphrases, one-open exact root-database snapshots and rollback copies, staged bootstrap-root identity binding, ordered root-database publication, cleanup-only resume, signal-safe mutation evidence, and final-Bash/Python recovery compatibility.
- Unified `platform-pki csr-recover` is Python-backed. Preserve pre-parse journal selection, exact TTY confirmation, kind-specific lifecycle-through-inventory or lifecycle-through-export locking, the under-lock no-switch journal recheck, final-Bash journal compatibility, permanent replay consumption, pre-commit rollback, and post-commit/finalization resume-only behavior. Only the durable Python-owned `response-signing` checkpoint may authenticate and adopt a post-sign/pre-evidence response signature; final-Bash-compatible `ca-committed` state must remove and recreate an otherwise safe unowned signature.
- `platform-bastion-policy` is a Python helper for public bastion access-policy validation and rendering; real policy data belongs in `platform-private`.
- User-facing behavior is documented in `README.md` and topic docs under `docs/`; update both the command help text and docs when changing flags, defaults, paths, or safety rules.
- `platform-tools` owns reusable bootstrap/operator helpers only. Real secret values and generated PKI state live outside Git under `~/.config/platform-infrastructure/`.

## Verification

- Use `make shell` for Bashly generation and shell linting in the rootless development container. Use `./scripts/in-test-container make <target>` for focused pinned tests, or `make container-check` to run all maintained checks across both containers. Do not mount host SSH keys, private config, PKI state, or the Podman socket into routine containers.
- Run `make generate` after changing Bashly source and `make verify-generated` to prove committed executables are deterministic and current. Never edit a Bashly-generated `bin/` file directly.
- Run `make verify` after tool changes; it runs `bash -n` over maintained Bash files and `python3 -m py_compile` over maintained Python tools.
- All maintained tests are pytest-orchestrated. They must preserve real generated commands, external tools, executable fakes, PTYs, inherited descriptors, and SSH transport as subprocess boundaries rather than replacing them with in-process mocks.
- Run focused Make targets or pytest modules through the test container while developing. Reserve `make container-check`, which owns one complete `make test` execution in the pinned test image, for final acceptance; do not run a separate full `make test` immediately before it.
- `make test` runs non-rollover targets with two bounded Make jobs, then runs the rollover suite alone with four pytest workers. `test-pki-service-renew-writer` runs its four managed cases serially before using the same bounded `PKI_PYTEST_WORKERS` setting with `--dist load` for the host-local module only; `test-pki-csr-candidate` and `test-pki-csr-trust-install` use that setting with `--dist load`. `TEST_MAKE_JOBS` and `PKI_PYTEST_WORKERS` accept 1 through 4 and are forwarded by `scripts/in-test-container`; use bounded values rather than `-j` or `-n auto`.
- Run `make test-python-infrastructure` after changing pytest fixtures or process helpers. Keep subprocesses argv-only with `shell=False`, isolated process groups, bounded descendant cleanup, and shell-style signal statuses. PTY and escaped-descendant supervision requires Linux procfs and pidfds.
- CSR signing, certificate-export, outcome-export, candidate, and schema-2 trust-install tests share one immutable session seed per pytest process; each test must use a metadata-preserving private copy with both managed OpenSSL configuration paths rebased and fresh signed exchange timestamps.
- Python-migration differential tests use `tests/pki/migration_contract.py` as the command/recovery inventory and `tests/pki/migration_harness.py` for metadata-aware snapshots. Preserve hard-link classes and within-tree identity transitions, normalize only declared dynamic fields, and never copy a crashed tree before recovery.
- Run `make test-pki-ca-rollover` after changing authoritative rollover scenarios; it uses four bounded pytest workers by default. Use `make test-python-pki-rollover` for explicit serial diagnostics.
- Run `make test-pki-root-create` after changing root authority creation, schema-3 writer journals, generation reservations, bootstrap publication, passphrase transport, or in-process rollback. Also run `make test-pki-ca-rollover-python-recover` when writer crash/recovery compatibility changes.
- Run `make test-pki-ca-rollover-parser` for the authoritative Python parser contract.
- Run `make test-pki-certificate-export` after changing immutable certificate export publication, resolution, CSR response validation, or its retained trust boundary.
- Run `make test-pki-csr-outcome` after changing authenticated terminal outcome export publication, signing, resolution, retained response trust, or package validation.
- Run `make test-pki-csr-candidate` after changing candidate evidence, outcomes, active pointers, renewal predecessor rules, or finalization recovery.
- Run `make test-pki-csr-issue-writer` after changing non-public host-local issue/migration writing, protocol authentication, CA publication, or writer-to-recovery handoff.
- Run `make test-pki-service-recover` after changing managed service transaction parsing, live preflight, rollback, cleanup, retained terminal evidence, or recovery checkpoints.
- Run `make test-command-contract` after command inventory or parser changes, and `make test-installed-tools` after installation or shared-asset changes. The latter uses a disposable `.tmp` install and an isolated runtime `PATH`.
- Run `make shellcheck` when ShellCheck is available; it lint-checks maintained shell tools and libraries.
- There is no CI workflow in this tree. For behavior not covered by maintained tests, run focused smoke commands in `/tmp/opencode` or another temporary namespace instead of the default `~/.config/platform-infrastructure/` paths.
- For PKI smoke tests, use `platform-pki init --namespace <temp-dir>` and pass `--namespace <temp-dir>` to every following `platform-pki <command>` so real CA material is never touched.

## Security And Generated Files

- Never commit generated archives, VM reports, SSH keys, token files, PKI CA material, service private keys, PKI exports, PKI backups, or copied private config.
- `reports/*` is ignored except `reports/.gitkeep`; use `reports/platform-vm-env-collect/` only for local analysis copies.
- PKI passphrase files are plaintext secrets; keep them outside Git, mode `600` or stricter, first-line passphrase length at least 16 characters with non-whitespace content, and prefer temporary secret-manager mounts such as `/run/secrets`.
- PKI rollover preparation requires a fresh generation-layout backup receipt, leaves `state/active-issuer` unchanged, and publishes immutable candidates plus public state under `state/rollovers/`. Root preparation also snapshots the reviewed private `pki/trust-consumers.yml`; deterministic candidate/state tree manifests record metadata and non-secret digests but never private-key or passphrase content. Keep pre-created child destinations, immutable write-ahead transaction manifests, identity-checked superseded/final manifest cleanup, full staged-source identities, backup-session rollback, and receipt-bound terminal unlink aligned; activation and later lifecycle transitions remain unavailable.
- PKI backups are encrypted with `age` by default; plain `.tar.gz` backups require the explicit `--allow-plain-backup` flag and still contain secrets.
- PKI operations use persistent shared lock files under `pki/locks/`. Acquire lifecycle before root, intermediate, inventory, and export locks as needed, release in reverse order, and hold locks across protected reads, mutations, and publication. After locking, normal commands must reject unresolved migration or rollover journals before reading operational snapshots.
- Legacy PKI state may prepare missing private control directories before locking, but only inventory installation, protected backup, and rollover status/migration may proceed. Under the full migration lock matrix, migration may also prepare missing empty private authority destination parents from older initializers and must revalidate the legacy layout before receipt-bound state checks or transaction creation. Normal CA and service commands must reject legacy or mixed authority layouts before operational reads or mutations.
- Service signing must reject OpenSSL include/global directives and signing paths outside staged CA state; snapshot validated publication destinations under lock and recheck identity immediately before each replacement.

## Tooling Notes

- `Containerfile.dev` uses a digest-pinned Debian 13 Ruby base, an immutable Debian snapshot with exact direct package versions, checksum-verified ShellCheck/shfmt binaries for `amd64` and `arm64`, and the locked Bashly bundle in `Gemfile.lock`. `Containerfile.test` separately uses digest-pinned Python 3.14, a matching immutable Debian snapshot, exact system packages, and a fully constrained pytest dependency graph; current final acceptance is `amd64`. Refresh each image's inputs together and verify both clean builds before `make container-check`.
- `make install` copies scripts to `INSTALL_DIR` and PKI templates to `SHARE_DIR`; custom installs commonly use `make install INSTALL_DIR="$PWD/.tools/bin" SHARE_DIR="$PWD/.tools/share/platform-tools"`.
- Installed PKI commands find templates through `PLATFORM_TOOLS_TEMPLATE_DIR`, checkout-relative templates, or `PLATFORM_TOOLS_SHARE_DIR`/XDG/default shared-data paths. They do not install or load PKI shell libraries.
- Proxmox helpers can stream themselves over SSH; remote prerequisites are `pveum` for token bootstrap, `qm` for VM cleanup, and remote `jq` only when `platform-proxmox-token-init --write-token-file` parses JSON output.
- `platform-proxmox-vm-cleanup` requires an interactive TTY and exact VMID confirmation unless `--yes` is supplied, rechecks exact VM identity/state before mutation, and authorizes streamed destruction with owner-only, bounded-lifetime state persisted on the Proxmox host; bearer nonces travel through framed stdin and protected FD 3, never SSH or child argv. Run `make test-proxmox-vm-cleanup` for fake-backed local and self-streamed SSH coverage.
- `platform-proxmox-vm-snapshot` uses generated create/list/rollback/delete subcommands, targets single-node Proxmox VE 9, and requires remote `pvesh`, `jq`, and Linux procfs at `/proc`, plus `qm` for mutations and local `jq` with `--ssh`; private action manifests are consumed before use and their descriptor is closed before operational children run. Create, rollback, and delete require a TTY unless `--yes` is supplied. Run `make test-proxmox-vm-snapshot` for fake-backed behavior checks.
- Real snapshot create, rollback, or deletion tests require explicit authorization and a disposable development VM. Keep environment mutations gated until `platform-infra` tags are reconciled and a dry-run target set is verified manually.
- The VM collector usually needs `sudo`; `COLLECT_ENV=1` and `INCLUDE_SENSITIVE=1` intentionally create more sensitive reports.
